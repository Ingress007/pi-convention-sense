# SnailJob 后端真实项目测试方案

> 被测仓库：`C:/DevelopmentProjectFiles/snail-job/snail-job`
> 插件版本：`0.3.0-guard.1`
> 策略：Observe-first；原仓库只读；修改测试使用 disposable Git worktree
> 状态：已完成；结果见 [`snail-job-results.md`](./snail-job-results.md)

## 1. 目标

1. 验证 Maven 多模块 Scope 是否准确；
2. 验证 Top-K peer 是否来自相同后端仓库、优先同 leaf module 与同 role；
3. 验证 High/Medium Observation 与源码结构一致；
4. 测量首次索引、缓存后分析、Context token 和 weak Snapshot 比例；
5. 验证真实 Pi read → Snapshot → Context 生命周期；
6. 验证 Guard 补救路径不会死锁；
7. 验证 prospective write、bypass、Branch 隔离和 Shell 后置检测；
8. 收集 Guard 生产准入指标。

## 2. 安全边界

- 原仓库不执行 edit/write，不修改 tracked 文件；
- `.pi` 日志若需落地，应加入 `.git/info/exclude`，不修改 tracked `.gitignore`；
- 所有 edit/write/Shell mutation 在 detached disposable worktree 中执行；
- 每个阶段前后比较 `git status --short`；
- 自动记录测试前 commit，worktree 测试结束后强制清理；
- 默认 `mode=observe`，Guard 只在隔离 worktree 显式启用。

## 3. 样本设计

目标 26 个，分层抽样：

| Role | 数量 | 重点模块 |
| --- | ---: | --- |
| controller | 6 | server-web |
| service-impl | 6 | server-web、openapi |
| mapper | 4 | datasource-template |
| request-dto | 4 | server-web model/request |
| response-dto | 4 | server-web model/response |
| service-interface | 2 | server-service |

选择规则：固定排序 + 文件大小分位，避免只挑相似或简单文件；结果保存目标相对路径，便于复现。

## 4. 阶段与自动化

### A. 安全和结构基线

- 分支、commit、dirty 状态；
- Maven leaf module；
- production/test Java 数量；
- role 分布；
- 项目约束文件和构建版本。

### B. 静态批量分析

对 26 个目标运行同一 `ObserveAnalyzer` 实例：

- repository root；
- Scope key/confidence；
- indexed/considered/selected 数量；
- candidate score 与 breakdown；
- Observation support/samples/confidence/status；
- Snapshot status、token、duration；
- 所有 candidate 是否在被测仓库内；
- candidate 是否同 role、同 leaf module。

输出机器可读 JSON 和 Markdown 汇总。

### C. 真实 Pi Observe

从被测后端根目录启动新 Pi 子进程，限制为 read-only 工具：

- 读取 Controller；
- 读取 ServiceImpl；
- 读取 Mapper；
- 读取 weak Service interface；
- 验证日志中的 repositoryRoot、Scope、candidate、Context 注入；
- 验证日志不包含源码或完整 prompt。

### D. Shadow Guard 指标

保持 Observe，计算每个模拟 mutation 的 `allow/wouldBlock/reasonCode`，不执行修改。统计：

- `TARGET_NOT_READ`；
- `SNAPSHOT_NOT_INJECTED`；
- `SNAPSHOT_VALID`；
- weak/no-peer fail-open；
- 潜在误拦截样本。

### E. Disposable worktree Guard

验证：

- unread edit block；
- read + Context + retry allow；
- prospective new file；
- one-time bypass；
- path exception；
- Branch 切换清理运行时授权。

### F. Shell 后置审计

分别验证：

- clean → dirty；
- already dirty → 再次修改；
- shell 修改并 commit 导致 HEAD 变化；
- Evidence 已覆盖与未覆盖文件；
- Context finding 注入和重新建立 Evidence 后消除。

### G. pi-lens 联调

- 诊断工具不进入 mutation Guard；
- Guard block 后无重复 lint/LSP 死循环；
- edit 放行后由 pi-lens 承担编译/LSP/格式检查。

需要安装、认证或 TUI 操作时再请求用户介入。

## 5. 准入指标

| 指标 | 门槛 |
| --- | ---: |
| Top-K 候选人工/语义认可率 | ≥ 80% |
| 高置信 Observation 准确率 | ≥ 90% |
| Observe 潜在误拦截率 | ≤ 10% |
| 平均 Snapshot token | ≤ 1200 |
| Branch/Repository 串用 Snapshot | 0 |
| Guard 永久阻塞 | 0 |

自动指标不能替代业务语义判断。无法自动确认的候选会进入人工复核清单，而不是计为通过。

## 6. 已发现并关闭的问题

首次从插件仓库会话读取外部 Java 文件时，旧实现错误使用 `ctx.cwd` 建索引，导致 snail-job 目标引用 `test/fixtures` peer。已完成：

- 目标路径 Git/Maven repository root 解析；
- Snapshot 记录 `repositoryRoot`；
- 多根 Context 相对路径；
- 跨仓库污染回归测试；
- request/response package 对泛化 `*VO` 角色的覆盖；
- additive signal 不再被错误标记为互斥 Mixed。

修复后跨仓库回归测试要求所有 candidate 都位于目标 Git repository 内。

执行阶段又关闭了以下问题：

- `Generated by ... DO NOT EDIT` 源码头未被识别；
- DTO 缺少命名、Lombok、Bean Validation 与 Serializable Evidence；
- `request` 目录下普通 Handler 被误判为 DTO；
- 同 Scope 多个 Snapshot 重复注入；
- token 裁剪后的候选标题未显示 `showing X of Y`；
- Scope key 被 formatter 截断。

## 7. 用户介入点

仅在以下情况请求用户操作：

1. pi-lens 需要安装或授权；
2. TUI `/tree`、`/convention-bypass` 必须人工交互验证；
3. 候选在技术上同 role/module，但需要业务语义确认；
4. 测试要求使用用户本地依赖、数据库或私有配置。
